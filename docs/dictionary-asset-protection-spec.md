# SPARXSTAR Dictionary — Asset Protection Specification (draft v0.9.1)

**Asset:** the SPARXSTAR Dictionary corpus (entries, definitions, examples, etymologies, audio, and the compilation itself), served at `wp-json/sparxstar/v1/dictionary` from the `system-core`-fronted WordPress deployment.
**Premise:** this is owned intellectual property and the platform's most valuable data asset. CORS and API keys visible to browsers are **not** protection. Anything publicly readable is publicly copyable; protection is therefore layered: minimize exposure, throttle and detect bulk extraction, make copies provable, harden the write surface, and hold a real legal position.
**Status:** draft v0.9.1, **ADR-ready** — not ratification-ready, deliberately: numeric budgets, field projections, the approved-consumers list, credential lifecycle, and cutover acceptance tests are the ADR's decisions to make, and this spec intentionally leaves them open. Owner decisions in force: machine-to-machine only at target state (§1), gated cutover with a documented browser-access migration exception until it verifies (§1.4), temporary sunsetted CORS measure active in `system-core` (§1.4), no false content in the corpus ever (§4). Sections are the single source of truth; this line restates nothing else. Full decision lineage: see Changelog at the end of this document. Sweep rule: every version's model changes retire words AND assertions — the sweep greps both across the whole document, and the empty grep ships as evidence.

## 1. Access model (DECIDED — owner ratified: system-token, machine-to-machine only)

**TARGET STATE: the Dictionary API serves only approved SYSTEMS holding a service credential. Humans — authenticated or anonymous — never call it, and user identity plays no role in its auth.** Browsers call their own system's backend; that backend calls the dictionary. **Migration exception (documented, sunsetted):** until the §1.4 cutover verifies, the deployed browser app's direct access continues under the temporary CORS measure; every clause in this section describes the state that begins at cutover.

| Caller | Access | Enforced by |
|---|---|---|
| Approved systems (games backend, game service/engine, payload build pipeline, future WordPad backend) | lookups and capped pagination over the ADR-defined field allowlist, within a per-system rate ceiling sized to that system's legitimate need | per-system credential verified by the plugin; edge pre-filter 401 on missing `Authorization` |
| Browsers / end users (including authenticated writers) | **none at target state** (the §1.4 migration exception applies until cutover). They interact with consuming systems, which mediate | credential never present client-side; route refuses browser origins |
| Operators | bulk export, dumps, admin listings | never on the API; WP admin / offline tooling only, audited (T2 unchanged) |

### 1.1 The credential is server-side only — a browser is never a "system"
Any credential that ships in browser-delivered code is burned on arrival, whatever it is named (`X-Api-Key` was this failure; it stays retired). CI/lint guard: the games frontend and all browser bundles are scanned for the credential pattern; a hit fails the build. Tripwire (reuses the temporary CORS PR's route regex `~^/wp-json/sparxstar/v1/dictionary(?:/|$)` in nginx alerting once cutover completes), with honest severity — a preflight proves an ATTEMPT, not a leak, since any webpage or scanner can cause one without holding any credential:
* OPTIONS or `Origin` header alone → **anomaly, investigate**: an attempted browser-side integration (scanner, stray fetch, or a frontend that regressed).
* `Origin` header on a request bearing a **valid system credential** → **PRIORITY_1 critical indicator** (`[BREACH_DETECTED]` log prefix), not proof — server-side HTTP libraries can emit Origin headers. Response posture: treat the credential as burned, rotate fast with human confirmation on first occurrence (auto-rotation on a single event lets a misconfigured legitimate consumer self-DoS the platform), automatic on repetition.
* **Arming rule:** the tripwire is armed only AT cutover (§1.4). Before cutover the deployed browser app legitimately calls this route, and an armed tripwire would page on every player.

### 1.2 Per-system credentials, not one shared token
One credential per consuming system. Rationale: leak attribution (which system lost it), independent rotation (no synchronized outage), independent revocation, and **per-system ceilings sized to legitimate need and expressed primarily as ROLLING UNIQUE-ENTRY BUDGETS** (distinct entries served per credential per rolling window — this bounds corpus exposure directly, which is the protected quantity), with request-rate limits secondary. **Budget accounting requires an atomic, durable store** — `(credential_id, entry_id, window)` with race-safe insert-if-absent counting (a WordPress custom table with a unique index, or Redis with SETNX), surviving restarts, with a scheduled purge of rows older than the rolling window (purge keeps the table performant; never purge inside the live window). The games broker's budget is its real daily word need, so even a fully compromised consumer system cannot bulk-harvest the corpus under its own credential: it exhausts its unique-entry budget in minutes and alarms. A single shared "THE token" is rejected (see Rejected list).

Implementation, two acceptable forms:
* **Interim (ships now):** per-system static secrets — long random values, stored only in server environments/secret managers, hashed at rest on the WordPress side, presented as `Authorization: Bearer`, rotation runbook with per-system schedule.
* **Target (consistent with the platform):** `id.sparxstar.com` issues short-lived machine tokens (client-credentials grant; one client identity per system; `aud: dictionary`, per the one-token-one-audience doctrine), and the plugin verifies RS256 against the same JWKS every other verifier uses. Requires a client-credentials endpoint on the identity node — scheduled work, not a blocker for the interim form.

### 1.3 The whole WordPress surface is in scope, not just the route
Locking `wp-json/sparxstar/v1/dictionary` is void if entries leak via WordPress's other doors. Required: the dictionary post type / tables are NOT exposed through default `wp/v2` REST routes (no public `show_in_rest`, or capability-gated); no public single/archive permalinks or templates; excluded from WP search, sitemaps, and feeds. Verification is a **CI-resident negative matrix** that ENUMERATES rather than guesses: it fetches the `wp-json/` index (e.g., `wp rest route list --format=json` via wp-cli in the build container) and fails the build on any route **in the Dictionary namespace or exposing dictionary content** that is not on the approved list — scoped to Dictionary, not to every route containing `sparxstar`, so unrelated legitimate plugins don't break builds; it also lists registered post types and asserts none exposes entry content, then exercises the concrete surfaces — global search (`/?s=`), default REST (`/wp-json/wp/v2/<enumerated rest_base>`), permalinks, feeds (`/feed/?post_type=...`), oEmbed (`/wp-json/oembed/1.0/embed?url=...`), author archives, and sitemaps — failing on any 200 with entry content.

**Media files are their own leak (§1.3a):** if dictionary audio — recorded speakers, the most irreplaceable layer — sits in the WordPress media library, the files are directly fetchable at guessable `/wp-content/uploads/` URLs no matter what REST does, and uploads paths are date-structured and walkable. Required: dictionary media moved out of the public uploads path, and — consistently with §1.1, since browsers never hold system credentials, a credential-gated media URL would be unplayable by the only clients that play audio — **protected audio flows through the broker**: the broker proxies/streams it, or issues short-lived signed URLs scoped to a session. On the WordPress side, the internal media gate uses nginx `auth_request` to a deliberately lightweight plugin endpoint (early-hook/minimal-load, not a full WordPress bootstrap per file), because nginx alone cannot validate hashed credentials (§2). Attachment pages disabled; the negative matrix includes a direct-file-URL case per media type, expecting 401/404 from the raw path.

### 1.4 Migration dependency — the deployed reality gates everything (DECIDED sequencing)
**As deployed today, the games app is a static browser application calling this API directly.** M2M is therefore a cutover, not a configuration flip: parking CORS now breaks production, and enforcing credentials now locks out every player. The sequence, each step gating the next:
1. Build the consuming-system path. **Broker (owner ruling, supersedes the earlier RLC recommendation): ESU — the Sky workshop system** holds the Dictionary credential and serves the games (packs out, observations in, per the Governed Outputs doc Part II); verify ESU's deployment, auth, and storage reality during the Sky repo review before the cutover milestone is scheduled. Recorded fallback: the RLC/Game Node — it is deployed, authenticated, rate-limit-disciplined, outbox-equipped, and `rlc-api.sparxstar.com` ALREADY serves CORS for `games.sparxstar.com`, so a dictionary proxy route there keeps the frontend on an origin it already trusts, needs exactly one Dictionary credential, and makes the temporary WordPress-edge CORS evaporate at cutover. **The broker exposes PURPOSE-BUILT game endpoints, never a transparent Dictionary proxy** — a pass-through would merely relocate the enumeration surface. Routes are shaped like game needs (e.g., a daily puzzle set, a session-scoped word fetch), not like dictionary queries: no lookup-by-arbitrary-key, no search, no pagination reaches the browser. Constraint carried over: these routes serve guests, so they are anonymous-safe and heavily capped (the broker's onward-exposure budget per §1.6). Alternative: the payload pipeline (pre-cut game content from the games origin).
2. Verify it live in production alongside the existing route.
3. Switch the games frontend to it; verify no browser traffic remains on the dictionary route (observed, not assumed — the pre-armed tripwire in monitor-only mode is the measurement).
4. Only then: remove CORS from the route, arm the tripwire (§1.1), enforce system credentials, and retire the browser path.

**Until step 4, the existing route and its CORS behavior stay working.** The scoped CORS preflight PR in `system-core` is UN-parked and may ship as an **explicitly temporary** measure — it narrows an integration that already exists, which beats the status quo — carrying in its description AND as a Death Clock comment in the config itself (`# TEMPORARY — expires at M2M Cutover. Ticket: <tracker-ID>. Do not extend.` — the concrete tracker ID is mandatory, not a placeholder): a sunset clause tied to the cutover milestone, a tracking issue, and the note that `X-Api-Key` remains architecturally condemned (§1.1) even while temporarily served. Its regex and negative-test discipline transfer to the tripwire at cutover.

### 1.5 No full-dump or unbounded-list endpoint exists on the API. Ever.
Bulk export remains an internal, audited operation.

### 1.6 End users and guests
Resolved by construction: guests and account holders alike receive dictionary content only through consuming systems — pre-cut game payloads or system-mediated features. What each consuming system may expose onward (payload size, fields) is that system's ADR-governed budget, and the per-system ceiling (§1.2) is its hard bound.

## 2. Anti-enumeration and rate control (edge layer)

At Cloudflare (preferred, before origin) and mirrored at nginx (defense in depth):

* Rate limits on `wp-json/sparxstar/v1/dictionary*` keyed **per system credential** with per-source-IP as backstop, sized for a human using the product, not a crawler (numbers ADR-set; the property: a full-corpus walk takes days and trips alarms). M2M does not retire throttling — a compromised consumer system can still try to walk the corpus under its own credential; the per-system ceiling (§1.2) is what stops it, and attribution names the system.
* Response caps in the plugin for every caller: page size ≤ N, search results ≤ 20, no `per_page` override beyond the cap, total-results counts rounded or omitted (an exact corpus count is a scraper's progress bar).
* Page tokens: opaque, signed, expiring (minutes), bound to the issuing key/IP class — a harvested token from one client must not resume another's walk.
* Cloudflare bot management / WAF on the route. **Edge caching of dictionary responses is OFF (explicit bypass rule)** — under M2M the callers are a few ceiling-capped systems the origin serves trivially, and caching authenticated responses without a proven cache-key design risks cross-credential replay; the simple ruling is no cache.
* **Enforcement points, stated not assumed:** the WordPress plugin is AUTHORITATIVE for credential validation and per-system quotas — nginx cannot securely validate hashed credentials without an auth module, so nginx's roles are exactly three: reject missing `Authorization` (presence check), tripwire logging (§1.1), and per-IP backstop. Cloudflare contributes bot filtering and per-IP limits only; header-keyed rate limiting there is plan-dependent and not relied upon.
* **Page tokens are pagination cursors, never authentication or authorization:** opaque, signed, expiring cursors bound to the issuing credential's session — but possession of a token grants nothing without the credential, and no route treats a page token as an identity. (Interpreted from a truncated review clause; confirm at ADR.)
* Robots.txt and user-agent rules on the route are **deterrence and noise reduction only — never security**. They exist to filter honest crawlers so rate limits and enumeration alarms see cleaner signal; no security property in this spec may cite them, and no test may treat their presence as a control.

## 3. Detection and response

* Log every dictionary request with system credential ID, source IP, route, and page-token lineage. **Credential values are redacted from every log at every layer** — nginx access logs must not capture the `Authorization` header (strip or hash-prefix it), plugin and application logs record credential *IDs* only, and the CI log-hygiene check greps deploy artifacts and sample logs for credential patterns.
* Alert on enumeration signatures: sequential/near-sequential token walks, breadth-first key coverage, sustained rates near the cap, many distinct entries per IP per hour.
* **Honey endpoints and honeytokens (deception in infrastructure, never in the corpus):** plausible-but-fake surfaces whose only function is to alarm — e.g., an unadvertised `/export` or `/dump` route that returns 404 and pages on any touch; a decoy credential planted where only an intruder rummaging configs would find it, monitored for use; unused path patterns that alert on access. High-signal by construction: under M2M the legitimate caller list is short and known, so any touch of a honey surface is an intruder or a misconfigured system, both worth waking someone for. The honey inventory lives in T2, and no honey artifact ever contains or implies false linguistic content — the §4 hard rule is untouched.
* A documented response runbook: throttle → **revoke the system credential** (per-system credentials make this surgical) → block source → rotate. Who may pull each lever, and evidence retention for legal follow-up. Plus the §1.1 tripwire: CORS preflight or credential-in-bundle detection alerts immediately.

## 4. Provenance — make copies provable, without corrupting the corpus

**Two meanings of "provenance" — do not conflate them.** Data-lineage labels (source, verification status, confidence — e.g., a `verification: pending` field) are welcome *editorial metadata* for corpus quality and research use; they are stripped in seconds by any copier and have zero anti-copying value. This section is about the second meaning: evidence that a copy is a copy. Reviews proposing lineage tags as protection are answered here.

**Hard rule: the corpus at rest contains only true linguistic records.** Fictitious "trap entries" (the commercial-dictionary mountweazel tradition) are prohibited here: for a dictionary of record, every false entry misleads learners, contaminates research and any model trained on the corpus, and spends community trust to buy evidence. Provenance is achieved by non-corrupting means, with an honestly stated trade-off: these are weaker proof-of-republication than a planted fake, so the spec compensates by leaning harder on priority evidence and extraction-time detection.

* **Authored-expression fingerprinting (primary mechanism):** every definition, example sentence, usage note, and cultural/etymological note is **original authored prose** — true content, uniquely expressed. Facts and meanings are unprotectable; expression is, so systematically original prose makes every entry its own copyright-backed fingerprint: verbatim or near-verbatim reappearance elsewhere is evidence of copying. Requirements: (a) no definition or example prose imported, adapted, or translated from existing dictionaries — this is rights hygiene for our own ownership as much as fingerprinting; (b) authorship recorded per entry (feeds §7's contributor agreements); (c) concentrate expressive originality in the long-form fields — short bilingual glosses carry no uniqueness, examples and notes carry it all; (d) maintain a shingle/n-gram similarity index of corpus prose (T2 tooling) so suspected copies and third-party datasets can be *scanned* for overlap rather than inspected by hand. Known limit: paraphrase defeats verbatim matching — but paraphrasing a whole dictionary is costly, partial paraphrase leaves detectable overlap, and wholesale paraphrase of the compilation may still infringe (counsel question, §7).
* **Serving-layer selection/ordering watermarks:** where an entry legitimately has multiple true example sentences, sense orderings, or accepted orthographic variants, the choice and order served varies deterministically per consuming system (credential). Everything served is true; the selection pattern is the fingerprint. Primary use: identifying *which* surface a leaked dataset was harvested from. The mapping lives in T2 only.
* **Priority-of-authorship evidence (the legal backbone):** dated, hash-anchored archival snapshots (§6) plus the retained editorial changelog (§5). This proves the corpus existed here first, corrupts nothing, and is the package counsel actually litigates with.
* **Extraction-time detection over republication-time proof:** the §3 enumeration alarms and attribution (every walk is credential-bound to a named system) carry more of the protective weight — catching the harvest in progress beats proving the copy afterward.
* Response-level metadata fingerprints (request IDs, per-key ETag salts) may aid leak-surface identification but are assumed stripped by any competent copier; they are diagnostics, not evidence.

## 5. Write-surface hardening (the master copy lives in WordPress)

The WP install is now the custodian of the crown jewels; its admin is the highest-value write surface in the constellation.

* Admin: MFA mandatory for every account that can touch dictionary data; least-privilege roles (editors of dictionary content need not be WP admins); no shared accounts.
* Attack surface: XML-RPC disabled; application passwords disabled or audited; REST **write** routes for the dictionary restricted to authenticated editor capability + nonce, never key-gated; plugin/theme sprawl minimized; core and plugins on a tested update cadence (the WP 7.1 review earlier in this program is now operationally relevant — updates are part of protecting the asset, and each field guide gets read against this spec).
* Editorial integrity: revisions retained for dictionary post types / custom tables; deletions soft and audited; and the editorial change log is **immutable — append-only and hash-chained**: each save appends a ledger event with a pinned recipe — **canonical serialization: RFC 8785 (JCS), the same library as the platform's revision IDs; algorithm: SHA-256; event ID: ULID (time-sortable, collision-safe); fields: `hash(JCS({eventId, entryId, timestamp, editorId, contentHash, prevHash}))`** — to a `dictionary_ledger` table, so no past definition can change without breaking the chain. **And the chain head is anchored off-infrastructure** — written into each §6 offline snapshot manifest (or any independent append-only location) on a **pinned schedule: at every snapshot, and at least weekly to the offline master even in weeks without a snapshot** — because a chain living entirely in one database can be recomputed wholesale by an attacker with DB root; the externally anchored head is what they cannot rewrite, and the mismatch is the proof. Tampering must be detectable even against editor or database credentials, which is what makes the lineage usable as §4 priority evidence.
* Hosting: WP admin not reachable from the open internet if operationally possible (IP allowlist or access gateway); separate staging; production origin only reachable via Cloudflare.

## 6. Survivability — the asset must outlive the deployment

* Automated, tested backups of the dictionary tables/post types on their own schedule, independent of whole-site backups; restore drills on the runbook calendar.
* **Offline archival masters:** periodic full exports (T2 operation) stored off-infrastructure (offline media + separate cloud account), hash-manifested and dated. **Pull-based, into versioned/immutable storage:** the backup system reaches into the database on its own credentials and schedule — never DB-push — so a compromised database server can neither overwrite backup history nor forge the §5 anchored ledger heads embedded in the manifests. The production database must never be the only complete copy.
* Export format documented and open (e.g., JSON/CSV + media manifest) so the corpus is never hostage to WordPress, a plugin, or a host.

## 7. Legal layer (engage counsel — this section is engineering's input, not legal advice)

### 7.1 Cultural stewardship (governing principle for every licensing decision)
This dictionary is guarded **for** its language community, not **from** it. The asymmetry, stated as spec text so no protection measure can quietly invert it:
* **Protected:** community access to the language through the products and appropriate channels; contributor rights — attribution for entry authors, informed consent and agreed terms for recorded speakers, and their standing in any future licensing revenue as counsel and the contributor agreements define.
* **Licensed, never free by default:** commercial redistribution, automated harvesting, and model training on the corpus. "Unauthorized model training prohibited" appears verbatim in the API Terms of Use and any data license.
* No security or licensing measure in this spec may be implemented in a way that reduces the community's legitimate access below what existed before the measure. Where protection and access conflict, the conflict is escalated to an ADR, not resolved silently by engineering.

* The compilation, definitions, examples, and audio are protectable works; a dictionary's strongest shield is often rights + terms, not code. Establish: ownership documentation (contributor agreements for every entry author/speaker), a clear Terms of Use on the API prohibiting bulk extraction, redistribution, and ML-training use without license, and a chosen license posture (all-rights-reserved vs. a deliberate open license for defined subsets or surfaces — an ADR-level cultural and business decision, especially for a national-language work where community access may be a mission goal).
* The archival hashes and editorial changelog (§4, §6) are the priority-of-authorship package that makes enforcement possible; serving-layer fingerprints (§4) support leak-surface attribution.

## 8. What this spec does NOT claim

* It does not make published content uncopyable — nothing can. No anonymous surface exists at the API; the only world-readable exposure is what consuming systems publish onward (e.g., game payloads), which is deliberately curated and budgeted (§1.6). The spec's job is to keep that onward surface thin, make any harvest slow, visible, and credential-attributable, and keep the full asset behind the system boundary and the legal line.
* Superseded note: earlier drafts treated the dictionary-route CORS PR as orthogonal, then parked; under §1.4 it is temporarily ACTIVE as a sunsetted migration measure and retires at cutover.

**Rejected (do not relitigate):** a single shared system token (unattributable leaks, synchronized-outage rotation, all-or-nothing revocation — §1.2); any credential in browser-delivered code (§1.1); fictitious trap entries (§4); robots/UA rules as security (§2); full-dump endpoints (§1.5); per-user tokens for dictionary access (superseded by the M2M ruling — user identity is the consuming systems' concern, not the dictionary's).

## 9. Delivery order — ADR first, then one focused PR per area

1. **Commission the governing ADR before any implementation.** It must decide, measurably: exact routes and the field allowlist per system; pagination mechanics and caps; the **cutover milestone and its verification criteria (§1.4), which every enforcement step below is gated on**; the approved-systems list and each system's rate ceiling and onward-exposure budget (§1.2, §1.6); interim-vs-target credential form and the migration trigger (§1.2); token verification specifics for the target form (`aud: dictionary`, clock skew, JWKS cache TTL); licensing posture (with counsel); and numeric rate limits with their measurement points. Every subsequent step implements this ADR and cites it. **The ADR is the Contract, not just the record:** the games, web, and legal owners sign it, because its hardest clause — no browser calls the dictionary, ever — is a breaking change to whichever roadmap assumed otherwise, and the cutover sequencing (consuming-system backend or payload path live BEFORE lockdown flips) is what makes that signature honest.
2. Consuming-system path first (§1.4 steps 1–3): Games backend/proxy or payload pipeline, verified live. Then plugin: route/field allowlist, page/search caps, count suppression on all responses. Regression tests incl. negative cases (over-cap requests, unbounded list attempts → 4xx).
3. Edge: Cloudflare rate rules + WAF on the route; nginx mirrors; cache rules. Evidence: observed curl matrix at, below, and above limits.
4. Opaque signed page tokens; system-credential verification on all routes (enforced at cutover per §1.4 step 4).
5. Detection: logging, enumeration alerts, response runbook.
6. Provenance tooling (§4, no false content anywhere): serving-layer fingerprint mapping + honey-infrastructure inventory (T2-held); prose shingle index; archival snapshot pipeline + offline master #1 with ledger-head anchoring (§5).
7. WP hardening checklist executed and evidenced (MFA on all admins, XML-RPC off, write-route audit).
8. Legal package with counsel: ownership docs, API ToU, license ADR.

Each area (plugin caps, edge rules, tokens, detection, provenance, WP hardening, legal) lands as its **own focused PR** with observed evidence per house discipline — no omnibus security PR. Steps 2–4 are the ones that convert "our dictionary is public" into "our dictionary is served."
