# 3iAtlas Dictionary — Tech Spec

> Bootstrapped from the current codebase (`AGENTS.md`, `.github/copilot-instructions.md`,
> source under `src/`). Reflects what exists today, not a roadmap. Status `draft` —
> not binding until promoted by the spec registry owner.

## Identity

The 3iAtlas Dictionary is the authoritative lexical data store and REST API
service for the 3iAtlas platform. It is a standalone WordPress plugin
(`sparxstar-3iatlas-dictionary`) with a React PWA frontend. Every other
3iAtlas tool (WordPad, RLC, Sound to Symbol, Games) consumes this repo's
REST API; this repo consumes from none of them.

## Role boundary

See `ROLE.md` for the full owns/does-not-own breakdown. Summary: this repo
stores and serves approved dictionary entries and renders the Browse/Play
experience. By design it does not intake or adjudicate new entries (DVE's
job), does not handle suite identity/auth (`sparxstar-identity`'s job), and
does not persist cross-tool game progress (3iAtlas Game Service's job). In
practice, a legacy WP-authenticated frontend form
(`Sparxstar3IAtlasDictionaryForm`) still allows logged-in users to add/edit
entries directly, which is not yet reconciled with that boundary — see
`OQ-009` in Open items.

## Architecture

WordPress plugin (PHP 8.2+, WordPress 6.8+) exposing a REST API namespace
`sparxstar/v1/dictionary`, plus a React PWA bundled via webpack/babel and
served from the plugin. Data is stored entirely in WordPress: a custom post
type (`aiwa-cpt-dictionary`) with ACF/SCF fields, no custom database tables.
Namespace root: `Starisian\Sparxstar\IAtlas` with subpackages `\api`,
`\core`, `\frontend`, `\includes`.

The platform direction (per `3IATLAS-SUITE-ARCHITECTURE-v1.0`) is moving PHP
processing toward Eshu MCP and storage toward Dheghom vault; this repo is
designed not to over-invest in new WordPress/ACF storage layers ahead of
that migration.

## Data model

CPT: `aiwa-cpt-dictionary` (slug is frozen — never change).

Key ACF fields: `aiwa_extract` (definition), `aiwa_translation_english`,
`aiwa_translation_french`, `aiwa_ipa_pronunciation`, `aiwa_phonetic`,
`aiwa_audio_file`, `aiwa_word_photo`, `aiwa_origin`, `aiwa_synonyms`,
`aiwa_antonyms`, `aiwa_example_sentences` (repeater: sentence, IPA,
phonetic, EN/FR translation). `aiwa_entry_uuid` is minted by DVE and
preserved verbatim — never regenerated by this repo.

Game mechanics data (scores, session state, learned-word records) lives
entirely client-side today, in IndexedDB (`aiwa-games-db`, stores
`game-sets`/`game-sessions`/`progress-outbox`/`learned-words` — see
`src/js/hooks/idbUtils.js`), with no prefix convention applied. The
`game_` (persistent user meta) / `_spx_` (session-scoped) naming rule from
`.github/copilot-instructions.md` governs any future server-side WP user
meta for this data and must never use `aiwa_`/`sparxstar_` — it does not
describe the current IndexedDB implementation.

Entry lifecycle states: `active`, `deprecated`, `merged`, `hidden`,
`withdrawn` — UUIDs are never deleted once published.

## API surface

Base namespace: `sparxstar/v1/dictionary`. Auth model (Webster Model):
ephemeral page token (`X-Page-Token`, 60 min TTL, `browse` scope) or
consumer API key (`X-Api-Key`, long-lived, SHA-256 hashed at rest,
10k req/day). Per-IP rate limit of 100/15min applies to all endpoints.

| Method | Path | Auth |
|---|---|---|
| GET | `/lookup` | page token or API key |
| GET | `/search` | page token or API key |
| GET | `/wordlist` | API key only |
| GET | `/languages` | page token or API key |
| GET | `/domains` | page token or API key |
| GET | `/game-set` | page token or API key |
| GET | `/word-of-day` | page token or API key |
| GET | `/page-token` | public (referer check + rate limit) |
| POST | `/spell` | public (rate-limited) |
| POST | `/progress/sync` | deprecated — frozen, do not build against |

Response envelope: `{ "success": true, "data": {}, "meta": {...} }`. Errors
follow the WordPress REST standard `{ "code", "message", "data": { "status" } }`.
`POST /spell` additionally returns a top-level legacy `results` key
(duplicated into `data.results`) for backward compatibility with older
clients — see `Sparxstar3IAtlasDictionarySpellChecker.php`. New endpoints
must not add similar legacy top-level keys; use the standard envelope only.

## Seams

- **DVE → Dictionary**: WP-CLI batch import only (`wp aiwa-dictionary import`). No live connection.
- **Dictionary → consumer tools**: one-way REST API. WordPad, RLC, Sound to Symbol read; none write back.
- **Dictionary → Game Service**: `useProgressSync` IndexedDB outbox, intended to sync via suite-JWT-authenticated calls to the 3iAtlas Game Service. Currently a no-op (OQ-002).
- **Dictionary ↔ sparxstar-identity**: not yet wired. Page tokens are server-minted HMAC, independent of suite identity; suite JWT auth for Play mode is planned but unimplemented (OQ-003).
- **Helios auth introspection**: stubbed (`// TODO: Replace with Helios token introspection` across `src/api/`) — intentional integration points, not debt.

## Dependencies

- WordPress 6.8+, PHP 8.2–8.4
- ACF/SCF for custom fields
- React (PWA) built with webpack/babel, pnpm-managed
- myCred (optional, listens for `aiwa_game_*` hooks; no-op if absent)
- No DVE, Sirus, Helios, Mḗh₁n̥s, or Dheghom runtime dependencies (standalone mode)

## Security and privacy

- WordPress Coding Standards + VIPWPCS enforced via PHPCS/PHPStan
- All user input sanitized, all output escaped per WP conventions
- No custom database tables, no raw SQL
- Rate limiting via WordPress transients only — no external infra
- `aiwa-cpt-dictionary` linguistic fields locked post-import; WordPress admins cannot edit them directly
- No `wp_nonce` / `is_user_logged_in()` on new user-facing endpoints — suite identity is the long-term auth path
